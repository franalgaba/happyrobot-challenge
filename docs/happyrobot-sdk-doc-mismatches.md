# HappyRobot SDK Documentation Mismatches

This document records mismatches found while integrating `@happyrobot-ai/sdk` with the HappyRobot live API for the inbound carrier sales POC.

The local SDK reference files and the installed SDK README describe several request bodies using older field names. The live API rejected those documented payloads with validation errors. The implementation was updated to match the live API behavior.

## Context

- SDK package: `@happyrobot-ai/sdk`
- Integration script: `scripts/happyrobot/sync-workflow.ts`
- Local docs consulted:
  - `reference/resources.md`
  - `reference/workflows.md`
  - `node_modules/@happyrobot-ai/sdk/README.md`
- Live API operation tested:
  - workflow variable upsert
  - MCP server registration and refresh
  - MCP streamable HTTP initialization and tool discovery

## 1. Workflow Variable Payload

### Documented Shape

The local docs show workflow variables as:

```ts
await client.variables.create("workflow-id", {
  name: "MY_VAR",
  value: "hello",
});

await client.variables.update("workflow-id", "variable-id", {
  value: "world",
});
```

### Live API Error

The live API rejected that shape:

```text
Request doesn't match the schema:
#/key/invalid_type: expected string, received undefined
#/value_production/invalid_type: expected string, received undefined
#/value_staging/invalid_type: expected string, received undefined
#/value_development/invalid_type: expected string, received undefined
```

### Working Shape

The live API accepted:

```ts
await client.variables.create("workflow-id", {
  key: "API_BASE_URL",
  value_production: "https://example.com",
  value_staging: "https://example.com",
  value_development: "https://example.com",
});

await client.variables.update("workflow-id", "variable-id", {
  key: "API_BASE_URL",
  value_production: "https://example.com",
  value_staging: "https://example.com",
  value_development: "https://example.com",
});
```

### Suggested Doc Update

Update `client.variables.create()` and `client.variables.update()` examples and type docs to use:

- `key`
- `value_production`
- `value_staging`
- `value_development`

Also clarify whether `name` / `value` are deprecated aliases, unsupported legacy fields, or intended only for older API versions.

## 2. MCP Registration Payload

### Documented Shape

The local docs show MCP registration as:

```ts
await client.mcp.create({
  name: "My MCP",
  url: "https://example.com/mcp",
});
```

### Live API Error

The live API rejected that shape:

```text
Request doesn't match the schema:
#/server_name/invalid_type: expected string, received undefined
#/server_url/invalid_type: expected string, received undefined
#/auth_type/invalid_value: expected one of "none"|"bearer"|"api_key"|"oauth2"
```

### Working Shape

The live API accepted:

```ts
await client.mcp.create({
  server_name: "Carrier Sales Hono MCP",
  server_url: "https://example.com/mcp/<path-token>",
  auth_type: "none",
});
```

### Suggested Doc Update

Update `client.mcp.create()` examples and type docs to use:

- `server_name`
- `server_url`
- `auth_type`

Also document valid `auth_type` values:

- `none`
- `bearer`
- `api_key`
- `oauth2`

The README already mentions OAuth2 behavior, but the main create example still uses the older `name` / `url` shape.

## 3. MCP Initialization Notification

### Observed Behavior

During MCP registration, HappyRobot sent:

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/initialized"
}
```

Our initial MCP endpoint returned an unsupported-method JSON-RPC error:

```text
Unsupported method: notifications/initialized
```

HappyRobot treated that as an MCP connection failure.

### Working Server Behavior

The MCP server now accepts the notification without returning a JSON-RPC error:

```ts
if (body.method === "notifications/initialized") {
  return c.body(null, 202);
}
```

### Suggested Doc Update

Document the expected MCP handshake sequence for Streamable HTTP servers, including:

1. `initialize`
2. `notifications/initialized`
3. `tools/list`

Clarify that `notifications/initialized` must be accepted as a notification and should not be treated as an unsupported RPC call.

## 4. MCP Tool Input Schema Shape

### Observed Behavior

HappyRobot rejected valid JSON Schema generated by `zod-to-json-schema` when each tool's `inputSchema` was a top-level `$ref`:

```json
{
  "$ref": "#/definitions/VerifyCarrierRequest",
  "definitions": {
    "VerifyCarrierRequest": {
      "type": "object",
      "properties": {}
    }
  }
}
```

The live validation error was:

```text
tools[0].inputSchema.type: expected "object"
tools[1].inputSchema.type: expected "object"
tools[2].inputSchema.type: expected "object"
tools[3].inputSchema.type: expected "object"
```

### Working Shape

HappyRobot accepted inline object schemas:

```json
{
  "type": "object",
  "properties": {
    "mcNumber": {
      "type": "string",
      "minLength": 1
    }
  },
  "required": ["mcNumber"],
  "additionalProperties": false
}
```

### Suggested Doc Update

Document that MCP tool `inputSchema` must be an inline JSON Schema object with:

```json
{
  "type": "object"
}
```

If `$ref` schemas are intentionally unsupported, call that out explicitly and recommend dereferencing generated schemas before returning `tools/list`.

## 5. Type Definitions Appear Stale

The installed SDK type files reference generated Zod route schemas, but the examples and apparent TypeScript inputs do not match live API validation.

Examples:

- `client.variables.create()` docs show `{ name, value }`, while live API requires `{ key, value_production, value_staging, value_development }`.
- `client.mcp.create()` docs show `{ name, url }`, while live API requires `{ server_name, server_url, auth_type }`.

### Suggested Doc Update

Update the generated SDK types, README examples, and resource docs together so:

- compile-time TypeScript examples match live API validation,
- resource pages match the SDK README,
- live API validation errors are reflected in request body docs,
- migration notes explain any renamed fields.

## Implementation Workarounds Used Here

The POC currently handles these mismatches by:

- matching existing variables by either `key` or legacy `name`,
- sending variable payloads with environment-specific values,
- matching MCP servers by either `server_name` / `server_url` or legacy `name` / `url`,
- registering MCP with `auth_type: "none"`,
- accepting `notifications/initialized`,
- flattening generated Zod JSON Schemas before returning MCP tools.

These workarounds are in:

- `scripts/happyrobot/sync-workflow.ts`
- `apps/api/src/mcp/routes.ts`
- `apps/api/src/mcp/tools.ts`
